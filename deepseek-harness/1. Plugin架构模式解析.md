**Everything is Plugin**, 在进入DeepSeek Harness（后面用dhs简称）的plugin世界之前，我们有必要花一些篇幅了解一下软件设计中的Plugin架构模式，以及常见的实现方式。

# 什么是Plugin
**插件机制** 是一种软件架构模式，它允许在不修改宿主程序核心代码的前提下，通过外部的、可插拔的模块来扩展或定制应用程序的功能。

**插件机制可以带来以下好处**

+ **开闭原则**：对扩展开放，对修改关闭——加新功能不碰核心代码。
+ **解耦**：核心只依赖抽象接口，不依赖具体实现。
+ **生态**：第三方可以独立开发、分发插件（如 VS Code 扩展、Eclipse 插件、Maven 插件）。
+ **按需装配**：不同部署只装不同插件，减小体积。

鉴于这些好处，很多软件设计人员对plugin都趋之若鹜。其中的OCP （**Open to extend Close to change**） 更是软件设计中难以逾越的高峰，无数人前赴后继，尝试用Plugin进入软件设计的乌托邦。虽然有VSCode和Chrome这样的成功典范，但也有OSGi和阿里中台这样的失败案例。

究其原因，还是要看场景。但凡是可控的、垂直领域，比如IDE，浏览器能成功的可能性比较大。因为其扩展点是有限可预测的。但凡是通用的，扩展点不可预期的，失败的可能性比较大。

Agent比较特殊，它既有垂直特性，比如所有的Agent都应该有Agent Loop，Function Calling， Session管理，工具注册等功能。同时，如果要和不同行业结合的话，就又具备了很大的不可预测性。使用Plugin扩展机制对Agent产品来说是比较合适的，这也是市面上Agent产品（OpenCode, Cursor, Codex等）的标配。然而像dhs这样把plugin做到极致，一切皆插件，dsh是首创。是噱头，还是颠覆，我们让时间去做评论。

在此，我们还是聚焦技术本身，不管是部分支持插件，还是一切皆插件，其本质都是**本体不动，功能扩展**。这种扩展在软件设计中，主要有两种实现方式**接口驱动（拉模式）** 和 **事件/钩子驱动（推模式）**。

# Plugin的实现方式
拉模式和推模式是实现Plugin的两种主要范式：

+ **接口驱动（拉模式）**：宿主程序掌握完全的控制权。宿主在需要时（如启动时、菜单点击时），**主动拉取**所有实现了指定接口的插件实例，并调用其方法（如 `plugin.execute()`）。插件是被动的“工具人”，宿主决定“何时做”和“做什么”。
+ **事件驱动（推模式）**：插件掌握部分主动权。插件在启动时**主动向**宿主的“扩展点”注册回调，之后宿主在特定时机（如提交commit、发送prompt）**主动推送**事件给所有注册的插件。宿主决定“何时触发”，但插件决定“如何响应”。

## 接口驱动
接口驱动，也就是我们通常说的面向接口编程，和策略设计模式是个道理。例如，**Java 的 SPI（Service Provider Interface）**、**Eclipse 插件体系**、**IDEA 插件**。插件必须完整实现宿主定义的 `Action` 或 `ExtensionPoint` 接口。

接下来，我们用TypeScript演示如何实现一个基于接口的插件框架

首先，需要定义接口契约：

```typescript
export interface PluginContext {
  logger: { info(msg: string): void };
  config: Record<string, unknown>;
}

export interface Plugin {
  name: string;
  register(ctx: PluginContext): void;
  execute(ctx: PluginContext): void;
  destroy?(): void;
}
```

其次，需要管理插件，包括加载、卸载：

```typescript
class PluginManager {
  private plugins = new Map<string, Plugin>();
  private ctx: PluginContext;

  constructor(ctx: PluginContext) {
    this.ctx = ctx;
  }

  /** 动态加载并注册 */
  async load(specifier: string): Promise<void> {
    const mod = await import(specifier);          // 动态导入
    const plugin: Plugin = mod.default ?? mod;
    if (this.plugins.has(plugin.name)) {
      throw new Error(`duplicate plugin: ${plugin.name}`);
    }
    plugin.register(this.ctx);                          // 生命周期：激活
    this.plugins.set(plugin.name, plugin);
    console.log(`plugin loaded: ${plugin.name}`);
  }

  unload(name: string): void {
    const p = this.plugins.get(name);
    p?.destroy?.();                                 // 生命周期：卸载
    this.plugins.delete(name);
  }
}
```

最后，是对插件的使用
```ts
// 1. 构建插件上下文（注入 logger 与 config）
const ctx: PluginContext = {
    logger: {
        info(msg: string) {
          console.log(`[info] ${msg}`);
    },
      },
    config: {
    greet: { punctuation: '!!!' },
      },
};

async function main(): Promise<void> {
    const manager = new PluginManager(ctx);

    // 2. 动态加载插件（按需装配，互不耦合）
    await manager.load('./plugins/greet-plugin.js');
    await manager.load('./plugins/metrics-plugin.js');
    
    console.log('--- loaded plugins ---');
    console.log(manager.list());
    
    // 3. 执行所有已加载插件（宿主主动拉取）
      console.log('--- executeAll ---');
    manager.executeAll();
    
    // 4. 执行单个插件
      console.log('--- execute(greet) ---');
    manager.execute('greet');
    
    // 5. 卸载单个插件（触发 destroy）
      console.log('--- unload metrics ---');
    manager.unload('metrics');
    
    // 6. 卸载剩余插件（优雅关闭）
  console.log('--- unloadAll ---');
  manager.unloadAll();
}
```

## 事件驱动
如果把接口驱动理解成策略设计模式，那么事件驱动可以理解为观察者设计模式。所谓不同的Plugins，就是观察者中对观察对象的不同的Observers，当特点事件（或者叫hook钩子）被处罚时，会触发Plugin或者Observer的自动执行。典型的实现有，**Git 钩子**（pre-commit）、**VS Code 插件**（注册 `onCommand` 和 `onDidSaveTextDocument` 等事件）。

接下来，我们用TypeScript实现一个简单的基于事件的hooks plugin demo。

首先，也是要定义契约，但是这里最重要的是回调函数，而不是
```ts
/** 钩子回调函数 */
export type HookFn = (...args: any[]) => void | Promise<void>;

export interface HookRegistry {
  /** 扩展点：插件注册回调，返回取消订阅函数 */
  on(event: string, fn: HookFn): () => void;
}

/** 插件上下文：logger + config + hooks（只能订阅） */
export interface PluginContext {
    logger: { info(msg: string): void };
    config: Record<string, unknown>;
    /** 钩子注册器：插件只能 on，不能 emit */
    hooks: HookRegistry;
}

/**
 * 事件驱动插件：通过 apply(ctx) 挂载回调
 * ctx.hooks 是 HookRegistry —— 插件无法触发事件
 */
export interface HookPlugin {
    name: string;
    /** 注册阶段：通过 ctx.hooks.on() 挂载回调，可读 config / 初始化资源 */
    apply(ctx: PluginContext): void;
    /** 卸载（可选）：释放资源 */
    destroy?(): void;
}
```
这里有个问题，为了回调函数HookFn的通用性，我们这里使用了any，这就以为着我们会丢失类型检查。这个问题，我们先放在这，后续在分析dsh插件的时候，我们看看他是如何解决的。

同样，我们需要加载插件：
```ts
  /** 动态加载并注册 */
    async load(specifier: string): Promise<void> {
        const mod = await import(specifier);
        const plugin: HookPlugin = mod.default ?? mod;
        if (this.plugins.has(plugin.name)) {
            throw new Error(`duplicate plugin: ${plugin.name}`);
        }
        plugin.apply(this.ctx); // 只传 ctx，hooks 已内嵌
        this.plugins.set(plugin.name, plugin);
        this.ctx.logger.info(`plugin loaded: ${plugin.name}`);
    }
```
最后，当宿主需要在扩展点调用插件时，会通过emit广播事件，然后注册该事件的hooks都会被调用。
```ts
  /** 宿主在恰当时机触发，按注册顺序串行 await */
    async emit(event: string, ...args: any[]): Promise<void> {
        for (const fn of this.hooks.get(event) ?? []) {
            await fn(...args);
        }
    }
```
