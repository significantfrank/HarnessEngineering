> 本文是「论文解读」系列的配套实践篇。论文解读从理论上剖析了 Cordis（DeepSeek Harness 之下的插件框架）的反应式依赖注入与可逆副作用；本文则把这些理念落到一个约 450 行的从零实现 `[cordis-demo](../src/cordis.ts)` 上，逐行回答四个"为什么"。
>

1. 插件可以是函数 / 类 / `{ apply }` 对象（或导出 `apply` 的模块）；
2. Context 是服务的仓库，服务按稳定的 `ctx.<name>` 暴露，按名查找而非 import；
3. `inject` 声明服务依赖，插件在所有必需服务就绪后才会启动——加载顺序由依赖表达；
4. 事件（`ctx.on` / `ctx.emit`）让插件间通信；
5. 注册是可逆副作用（`ctx.effect`），卸载时按注册逆序回退。



下面四个小节，每个都对应一个设计问题，并直接贴出 `src/cordis.ts` 的源码来回答。

# 为什么可以支持三种形态的插件？
Corids可以支持三种形态之一：

```typescript
// 形态一：函数插件（最常见）
export function apply(ctx: Context) {
  console.log('hello')
}

// 形态二：对象插件
export const plugin = {
  name: 'my-plugin',
  apply(ctx: Context) { /* ... */ },
}

// 形态三：Service 子类（需要暴露服务时使用）
export class MyService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'myService')
  }
}
```

答案是**联合类型（Union Type）**，如下代码所示，Plugin被定义为可以是函数、对象、类三种形态之一的联合类型。

```typescript
/** Supported plugin entrypoint shapes. */
export type Plugin<T = any> = PluginFunction<T> | PluginConstructor<T> | PluginObject<T>

/** Shared metadata understood by the plugin registry. */
export interface PluginBase<T = any> {
  name?: string
  inject?: Inject
  provide?: string | string[]
  Config?: any
}

/** Function plugin called with `(ctx, config)`. */
export interface PluginFunction<T = any> extends PluginBase<T> {
  (ctx: Context, config: T): any
}

/** Class plugin constructed with `(ctx, config)`. */
export interface PluginConstructor<T = any> extends PluginBase<T> {
  new (ctx: Context, config: T): any
}

/** Object plugin (or a module namespace) with an `apply(ctx, config)` method. */
export interface PluginObject<T = any> extends PluginBase<T> {
  apply(ctx: Context, config: T): any
}

```

在 TypeScript 中，`type`（类型别名）和 `interface`（接口）是定义类型的两种核心方式。区别是`interface` 可以自动合并和extends，但是type只能通过 `|` 和 `&` 进行联合，通常用于类型联合。

# 为什么可以在context上挂载新的service？
这主要得益于TypeScript的 `interface` 自动合并（Auto Merge）功能，以及TypeScript的声明合并（Module Augmentation）。

所谓的自动合并，就是如果`interface` 的名称相同，其属性会被自动合并：

```typescript
// Adding new fields to an existing interface
interface Person {
  name: string;
}

interface Person {
  age: number;
}

const p1: Person = { name: 'frank', age: 30 } // ok
const p2: Person = { name: 'frank'} // 提示age missing
```

另一个是TypeScript的**声明合并**，在我们的demo实现中，可以看到：

```typescript
import { Service } from 'cordis-demo-ts'
import type { Context } from 'cordis-demo-ts'

/** Make `ctx.logger` visible to TypeScript via declaration merging. */
declare module 'cordis-demo-ts' {
  interface Context {
    logger: LoggerService
  }
}
```

关于这个功能，在 [dhs tutorial](https://deepseek-harness.github.io/deepseek-harness/develop/cordis-tutorial/)中也有提到，其特别说明：**声明合并**（`declare module '@deepseek-ai/cordis' { ... }`）会为 Cordis 已经声明的接口添加你的条目，例如新 `ctx.greeter` 属性的类型或事件名称。

以上是给Context在类型上增加了`ctx.logger`, 从而让其它TS程序可以在编译时看见`ctx.logger`，真正在运行时能通过`ctx.logger`取到Service实例。真正挂载是 `Service` 构造调 `ctx._provide`里的 `Object.defineProperty(this.root, name, ...)` 在根 context 上定义自有属性。

# 反应式余效应是如何实现的？
在论文解读中，我们提到cordis的依赖注入（Dependency Injection）是做到了反应式（Reactive），**运行期间 dependency graph 一旦改变，组件生命周期自动发生变化。**

这种响应式是如何实现的呢？主要是通过`inject`, 以我们的demo为例，在greeter插件中有这样的声明`greeter.inject = ['logger']` , 表示greeter插件是依赖logger插件的，按照论文要求，被依赖的插件需要响应式的影响依赖插件。

greeter 之所以能被“唤醒”，是三件事配合的结果：**依赖靠 **`inject`** 声明**、**服务一注册就触发对所有 PENDING 纤程的重新评估**、`_getImpl`** 从根服务表里查依赖是否就绪**。logger 自注册服务的那一下，就是那个“触发点”。其完整步骤如下：

## 1）第一步：greeter 挂上时为什么是 PENDING
当greeter首先被加载的时候，我们会得到一个PENDING状态的greeter，因为此时logger还没有被加载，

```typescript
_refresh(): void {
  if (this.state !== FiberState.PENDING) return
  let ready = true
  for (const name of Object.keys(this.inject)) {
    const impl = this.ctx._getImpl(name)   // 查 'logger'
    this._impls[name] = impl
    if (!impl) { ready = false; break }    // logger 还没注册 → impl 为 undefined → ready=false
  }
  if (ready) this._start()                 // ready=false → 不启动
}
```

`_getImpl` 就是去根服务表查：

```typescript
_getImpl(name: string): any {
  return this.root._services[name]?.value   // 此时 _services.logger 不存在 → undefined
}
```

所以 greeter **不启动**，但已经躺在 `_allFibers` 里、状态仍是 `PENDING`。这就是 demo 第一行输出 `greeter state right after mount: pending` 的原因。

## 2）第二步：logger 挂上 → 自注册服务 → 触发唤醒
`ctx.plugin(LoggerService)` → 又一个 `new Fiber(...)`。它的 `_refresh()` 这次 `ready=true`（logger 没有 `inject`，循环为空），于是调 `_start()`

`_start()`（`:206`）**第一句**就把状态翻成 `LOADING`：

```typescript
_start(): void {
  const ctx = this.ctx
  this.state = FiberState.LOADING          // ← 关键：先把 logger 标成 LOADING
  let ret: any
  ret = invokePlugin(this.plugin, ctx, this.config)   // new LoggerService(ctx, config)
  ...
}
```

`invokePlugin` 发现 `LoggerService` 是个 class，走 `new LoggerService(ctx, config)`（`:423`）。`LoggerService` 构造调 `super(ctx, 'logger')`，进入 `Service` 构造（`:277-283`）

```typescript
this.ctx = ctx
this.name = name
ctx._provide(name, this, ctx.fiber)   // ← 把 'logger' 注册进 ctx
this.start?.(ctx)
```

`ctx._provide('logger', instance, loggerFiber)`（`:324-329`）：

```typescript
_provide(name, value, fiber) {
  this.root._services[name] = { value, fiber }                                   // 1) 写入根服务表
  Object.defineProperty(this.root, name, { value, configurable: true, ... })     // 2) 让 ctx.logger 能读到
  this._refreshDependents()                                                       // 3) ← 触发点：唤醒所有等待者
  return () => this._revoke(name, fiber)
}
```

注意：此刻 logger 自己的 `_start` 还没返回，logger 状态是 `LOADING`、尚未 `ACTIVE`。但 `ctx.logger` 这一刻已经可用了。

## 3）第三步：`_refreshDependents` 唤醒 greeter
`_refreshDependents()`（`:347-351`）遍历 `_allFibers`：

```typescript
_refreshDependents(): void {
  for (const f of [...this.root._allFibers]) {
    if (f.state === FiberState.PENDING) f._refresh()   // 只重评估 PENDING 的
  }
}
```

此刻表里是 `[greeter, logger]`, **greeter** 还是 `PENDING` → 调 `greeter._refresh()`, 这次 `_getImpl('logger')`（`:319`）返回的是**刚才 **`_provide`** 写进根服务表的 logger 实例**（`:325`），`impl` 真值 → `ready=true` → `this._start()`。**greeter 变 ACTIVE**。

# 可逆副作用是如何实现的？
每注册一个副作用（Effect）时，**立刻做“正事”**，同时把它返回的**撤销函数（disposer）压进一个栈**；fiber 卸载时，这个栈被**倒序排空**、每个撤销函数被 `await` 执行。于是 teardown 永远按 setup 的逆序可预测地回退。这就是“可逆”的含义。

## 1）disposer数据结构
首先，副作用的清理函数是被存放在可倒序排空的先进后出栈中，该数据结构是 `DisposableList`

```typescript
export class DisposableList extends Array<Disposable> {
  add(dispose) { this.push(dispose); let removed=false; return () => { ... splice ... } } 
  drain() { return this.splice(0).reverse() }                                      
}
```

注意`drain()`的代码是把栈**整个取出并倒序**——这就是“后注册先撤销”的来源。

## 2）effect注册
在我们注册插件的时候，会调用 `ctx.effect`， `Context.effect` 只是委派：

```typescript
effect(execute, label) { return this.fiber.effect(execute, label) }  
```

真正干活的是 `Fiber.effect`：

```typescript
effect(execute, label = 'anonymous'): Disposable {
  if (this.state === FiberState.DISPOSED) throw ...         // 已卸载不能再注册
  const locals: Disposable[] = []
  let draining = false
  const run = async () => {                                 // 组合撤销器
    if (draining) return                                    // 幂等：重复调用是 no-op
    draining = true
    for (const d of locals.splice(0).reverse()) {          //  局部倒序
      try { await Promise.resolve(d()) } catch (e) { this._report(e) }
    }
  }
  let result
  try { 
      result = execute() // 立刻执行“正事”
  } 
  catch (e) { this._fail(e); throw e }   
  collectEffect(result, locals, (e) => this._fail(e)) // 把返回的 disposer 收进 locals
  const dispose = () => run()  // 注意，这里不是运行run(), 而是函数包装句柄
  this.disposables.push(dispose)    // 把组合撤销器压进 fiber 栈
  return dispose            // 返回给调用方，可手动撤销
}
```

注意，这里的`locals` 是本插件自己的本地局部数组，因为Effect可能返回多个disposer，所以`locals` 在执行的时候也需要通过 `locals.splice(0).reverse()` 进行倒序，即先注册的资源后撤销。

## 3）disposer的三种形态
我们知道，撤销函数是通过context.effect的返回值来进行撤销的。这个逆向清理工作是实现**可逆副作用**的关键，是可选的，如果用户选择手动清理的话，返回值可以是function，Promise 或者是 `function*` yield 多个 disposer。

做到这点是如下代码，确保三种形态的返回函数都能被接收压栈：

```typescript
function collectEffect(result, bucket, fail) {
  if (result == null) return    // apply/effect 不返回也行
  if (typeof result === 'function') // 同步 disposer
      { bucket.push(result); return }                 
  if (typeof result?.then === 'function') // async apply
      { result.then(d => bucket.push(d), fail) } 
  if (typeof result?.[Symbol.iterator] === 'function') // 生成器
      { for (const d of result) bucket.push(d) } 
}
```

所以 `ctx.effect` 既能写 `return () => cleanup`，也能写 `async` 返回 disposer，还能用 `function*` yield 多个 disposer。这三条在类型上就是 `Effect`。

比如，我们demo中Timer插件，就是通过返回一个同步的清理函数进行逆向的。

```typescript
 /** Run `callback` every `delay` ms; the returned disposer stops it. */
  interval(callback: () => void, delay: number): Disposable {
    return this.ctx.effect(() => {
      const id = setInterval(callback, delay)
      return () => clearInterval(id as unknown as number) // 清理函数
    }, 'ctx.timer.interval()')
  }
```

## 4）自动逆向回收
虽然框架支持3中回收函数的形态，但更多的时候，我们不需要返回任何值，即框架会自动帮我们回收，不需要用户手动回收。

例如，我们在greeter中注册了下面事件：

```typescript
  ctx.on('greet', (who) => {
    ctx.logger.info(`${prefix}, ${who}!`)
  })
```

context在通过on注册的事件代码如下，其正是利用`ctx.effect`的能力，在卸载的时候，对刚才注册的事件进行移除。

```typescript
  /** Subscribe to an event; returns a disposer that removes the listener. */
  on(event: string, listener: Listener): Disposable {
    let set = this.root._listeners.get(event)
    if (!set) this.root._listeners.set(event, (set = new Set()))
    return this.effect(() => {
      set!.add(listener)
      return () => set!.delete(listener)  // 返回的同步disposer，删除listener
    }, `ctx.on("${event}")`)
  }
```

所以，事件监听器**不需要单独的清理机制**，它是框架在通过`ctx.on` 注册实践监听器的时候，复用了 `ctx.effect`进行监听器删除动作，于是监听器随所属 fiber 卸载自动摘除，这是Corids框架已经帮我们做好了的。

# 小结：四件事其实是同一件事
回头看这四节，它们并不是孤立的小技巧，而是同一个理念的四个切面：

+ **插件三态**用联合类型 + `invokePlugin`/`isClass` 分发，让"怎么写插件"变得自由；
+ **服务挂载**用声明合并（类型层）+ `_provide` 的 `Object.defineProperty`（运行时层），让 `ctx.logger` 既类型安全又真实可用；
+ **反应式依赖**用 `inject` 声明 + `_provide` 触发 `_refreshDependents` + `_getImpl` 查表，让"依赖一就绪，等待者自动启动"，加载顺序由依赖图而非调用顺序决定；
+ **可逆副作用**用 `ctx.effect` 立即执行正事、把 disposer 压栈，卸载时 `drain()` 倒序排空，让 teardown 永远是 setup 的精确逆序——而 `ctx.on` 也只是复用了这条回路。  
  把它们串起来，就是论文里那句话的落地：**运行期间 dependency graph 一旦改变，组件生命周期自动发生变化，且一切注册都可逆回退。** Doris 只用约 450 行就把这条链路跑通；生产级 Cordis 在此之上还加了反射代理、isolate 作用域、epoch 与异步重载/卸载等机制，但"心脏"就是这些。
